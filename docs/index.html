One repository interface.
Three kinds of database.

krossdb gives PostgreSQL, MySQL, SQLite, MongoDB, and Qdrant the same repository & Unit-of-Work surface, the same exception hierarchy, and the same retries, caching, and observability — so your application code depends on an abstraction, not a driver.

Why

Every backend, ad hoc — until now

Most projects that touch more than one kind of database end up with per-backend, copy-pasted data access code, inconsistent error handling, and no shared story for retries, caching, multi-tenancy, or observability.

WITHOUT krossdb

  • A different try/except shape per driver — asyncpg errors don't look like pymongo errors
  • Retry and backoff logic reinvented in every service that calls the database
  • Tenant filtering bolted on per-query, easy to forget on a new endpoint
  • No consistent correlation ID between a log line and the query that caused it

WITH krossdb

  • Every driver exception translated centrally into one krossdbError hierarchy
  • Circuit breaker + exponential backoff applied uniformly by the adapter layer
  • TenantScopedRepository makes isolation the default, not an afterthought
  • structlog + OpenTelemetry wired in from the first query, with correlation/tenant context
Architecture

One package, one layout per concern

Every domain entity is a Pydantic v2 model. Every mutating repository method supports an idempotency key. Every raised error is a krossdbError subclass — driver exceptions never leak past the adapter boundary.

src/krossdb/
├── core/          settings, exception hierarchy, driver-error mapper,
│                structlog config, correlation/tenant context
├── interfaces/    AbstractDatabaseAdapter, AbstractRepository,
│                AbstractUnitOfWork, AbstractCache, events/outbox
├── adapters/      one package per backend family
│   ├── relational/   Postgres / MySQL / SQLite via async SQLAlchemy,
│   │             read-write splitting across replicas
│   ├── document/     MongoDB via Motor
│   └── vector/       Qdrant
├── repositories/ backend-specific AbstractRepository implementations
├── uow/           Unit of Work implementations
├── cache/         Redis-backed cache-aside implementation
├── resilience/    circuit breaker + exponential-backoff retry
├── events/        in-process dispatcher + transactional outbox
├── observability/ metrics, tracing, audit trail
├── multitenancy/ tenant isolation helpers
├── factory/       DatabaseFactory — builds/owns every configured adapter
├── models/        shared Pydantic base models (Entity, AuditRecord)
└── cli/           `krossdb` console script (init, health, schema create)
What's inside

Enterprise concerns, handled once

Data access

Repository + Unit of Work

The same CRUD and query surface across every backend, with atomic multi-write transactions via SQLAlchemyUnitOfWork.

Consistency

Savepoint-based bulk insert

Partial bulk-insert success via savepoints, with task-local session binding that's safe under concurrent requests.

Resilience

Circuit breaker + backoff

Exponential-backoff retry and a circuit breaker sit in front of every adapter call, tuned per connection.

Multi-tenancy

Transparent tenant isolation

TenantScopedRepository injects tenant filtering automatically, driven by contextvar-based tenant context.

Caching

Redis cache-aside

A drop-in cache-aside layer plus a generic idempotency-key manager for safe write retries.

Events

Dispatcher + outbox

An in-process event dispatcher and a transactional outbox — in-memory or SQL table-backed — for reliable side effects.

Observability

OpenTelemetry + audit trail

Metrics and tracing helpers out of the box, plus an audit trail recorder for every mutation.

Logging

Structured, correlated, masked

structlog with correlation IDs and automatic PII/secret masking, threaded through contextvars.

Scaling reads

Master/replica routing

Weighted load balancing across read replicas for the relational adapters, configured per ConnectionConfig.

Quickstart

CRUD and a transaction, in one file

No external services required — this runs against an in-memory SQLite adapter. The full runnable version lives at examples/quickstart.py.

quickstart.pypython examples/quickstart.py
class Widget(Entity):
    name: str
    quantity: int = 0

config = ConnectionConfig(
    name="primary",
    kind=DatabaseKind.SQLITE,
    nodes=[NodeConfig(dsn="sqlite+aiosqlite:///:memory:", role=RoutingRole.MASTER)],
)

async with DatabaseFactory([config]) as factory:
    repo = SQLAlchemyRepository(factory.get("primary"), widgets_table, Widget)

    # basic CRUD
    widget = await repo.create(Widget(name="gizmo", quantity=10))
    updated = await repo.update(widget.id, {"quantity": 25})

    # an atomic transaction spanning multiple writes
    async with SQLAlchemyUnitOfWork(factory.get("primary")) as uow:
        await repo.create(Widget(name="widget-a", quantity=1))
        await repo.create(Widget(name="widget-b", quantity=2))
        await uow.commit()
